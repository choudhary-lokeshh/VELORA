# Android release and signing

## What this covers

How an Android release is versioned, signed, and made ready for a store — and, as importantly, which parts of that a person has to do because no repository can do them.

The decision behind it is [ADR-0031](../decisions/ADR-0031-android-native-build-pipeline.md). Nothing here has been performed: no keystore exists, no Play Console account exists, and no artifact has been uploaded anywhere.

## Versioning

`apps/mobile/android-release.json` is the only source, and a person edits it:

```json
{ "version": "0.1.0", "versionCode": 1 }
```

`version` is what a person reads in the store listing and in Settings. `versionCode` is what Google Play orders uploads by: it must be a positive integer, must be strictly higher than the last accepted upload, and cannot exceed 2,100,000,000.

**Who advances it.** Whoever cuts a release, in the commit that cuts it. Not CI, not a build script, and not a local `expo start` — a version that moves on its own means the same commit produces different binaries, and a version that moves on every dev run puts a bump in everybody's diff.

`pnpm android:verify` refuses a malformed value, one over Play's ceiling, and one that has moved backwards from `origin/main`. When `origin/main` cannot be read it says so rather than counting the comparison as passed.

## Signing

### What exists

Three things, and they are deliberately separate:

| | Key | Where it comes from |
|---|---|---|
| Debug builds | The template's shared debug key | Regenerated by every prebuild. Published in every React Native project on the internet, secures nothing, and is fine for exactly this |
| Release builds | An upload key | Supplied at build time. Does not exist yet |
| Store distribution | The app signing key | Held by Google Play App Signing, created when the first upload is accepted. Never held here |

**The release build type cannot reach the debug keystore.** The bare template wires it there and `apps/mobile/plugins/with-velora-android.ts` replaces that line rather than adding beside it, so there is no path back. `pnpm android:verify` fails if one reappears.

### Supplying the upload key

Four values, from the environment or from Gradle properties, and never from a committed file:

| Environment variable | Gradle property |
|---|---|
| `VELORA_ANDROID_KEYSTORE_PATH` | `velora.android.keystorePath` |
| `VELORA_ANDROID_KEYSTORE_PASSWORD` | `velora.android.keystorePassword` |
| `VELORA_ANDROID_KEY_ALIAS` | `velora.android.keyAlias` |
| `VELORA_ANDROID_KEY_PASSWORD` | `velora.android.keyPassword` |

### What happens when they are absent

The release build **succeeds and produces an unsigned artifact**, with a warning saying so. That is deliberate: Google Play refuses an unsigned bundle, so the failure lands where it belongs rather than one step later, and no artifact is ever signed with a key that secures nothing.

A release pipeline additionally passes `-Pvelora.android.requireSignedRelease=true`, which turns the absence into a build failure instead of an unsigned file. Use it anywhere an unsigned output would be mistaken for a releasable one.

`pnpm android:build` reports the signing state of every artifact it produces, reading it back out of the file with `apksigner` rather than inferring it from the configuration.

### Provisioning the upload key — human-owned

Not performed, and not performable here. In order:

1. Generate a keystore on a machine that is not a build agent:
   `keytool -genkeypair -v -keystore velora-upload.jks -alias velora-upload -keyalg RSA -keysize 4096 -validity 10000`
2. Put it in the approved secret manager, alongside its two passwords and its alias. It is never committed, never attached to an issue, and never pasted into a build log.
3. Provision the four values into the release environment only.
4. Enrol in Play App Signing at the first upload, so Google holds the distribution key and the upload key can be rotated if it is ever lost.

The secret manager itself is an unresolved decision — the same one `AUTH_ACCESS_TOKEN_SIGNING_KEY` waits on. See [DECISIONS_REQUIRED](../decisions/DECISIONS_REQUIRED.md).

**Losing the upload key** is recoverable through Play support only if App Signing is enrolled. Losing an app signing key that Google does not hold ends the application's identity permanently.

## Build profiles

`apps/mobile/eas.json` declares three, all Android, none with an iOS counterpart:

| Profile | Output | Distribution | `EXPO_PUBLIC_APP_ENV` |
|---|---|---|---|
| `development` | debug APK with the development client | internal | `local` |
| `preview` | release APK | internal | `preview` |
| `production` | release AAB | store | `production` |

Everything in `eas.json` is compiled into the binary and readable by anyone holding it, so only `EXPO_PUBLIC_*` values appear there. `pnpm android:verify` fails on any other key, on anything that reads like a credential, and on a `submit` block — store submission is owned by a person with a Play Console account, not by this repository.

The same profiles build locally without EAS: `pnpm android:build` runs the equivalent Gradle tasks directly, which is what CI uses.

## Play Store technical readiness

What the artifacts already satisfy:

| Requirement | State |
|---|---|
| Application id | `com.velora.consumer`, permanent from first publish |
| Target API level | 36, which Play requires of a new application from 31 August 2026 |
| Minimum API level | 24 |
| 64-bit native code | `arm64-v8a` and `x86_64` present; asserted by `pnpm android:build` |
| App bundle | Release AAB produced |
| Uncompressed native libraries | `expo.useLegacyPackaging=false` |
| Permissions | Six, each justified; three blocked. Asserted as an allow-list |
| Adaptive and themed icons | Foreground, background colour, and monochrome layers |
| Not debuggable in release | Asserted against the built artifact |
| No over-the-air code updates | `expo.modules.updates.ENABLED=false` |

What no repository can produce, and what nobody has done:

- A Google Play Developer account and a Play Console entry
- The upload key above
- Store listing text, screenshots, and a feature graphic
- Content rating questionnaire answers
- A Data safety declaration
- A published privacy policy URL
- Target audience and ads declarations
- Any submission or release to any track

**Whether a Consumer Mobile application may be published at all** once mature content is enabled on Consumer Web is an open legal decision recorded in [DECISIONS_REQUIRED](../decisions/DECISIONS_REQUIRED.md) and marked `LEGAL REVIEW REQUIRED`. Technical readiness is not permission.
