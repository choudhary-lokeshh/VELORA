# Data and migration discipline

## Purpose

Define safe PostgreSQL 18 schema evolution while preserving domain ownership. Drizzle through Bun SQL owns typed data access and committed SQL migrations remain review authority under the unaffected portions of [ADR-0006](../decisions/ADR-0006-database-data-access-migrations.md) and [ADR-0016](../decisions/ADR-0016-bun-elysia-redis-bullmq-backend.md).

`0001_auth` adds the AUTH-owned tables and every constraint that protects an AUTH invariant, including the partial unique indexes for one live refresh token per family and one live refresh family per installation. It creates no table any other domain owns.

`0003_users_onboarding` adds the two append-only evidence tables USERS uses for admission: `users_policy_acknowledgements`, with the unique index that makes re-acknowledging a version a no-op, and `users_adult_assurances`, whose sequence identifier gives a total order over assessments recorded in the same instant. Constraints refuse an unknown assurance class or outcome, a self-declaration carrying provider evidence, an expiry dated before its decision, a malformed region, and an evidence reference that is not a digest.

`0002_users` adds `users_accounts`, the USERS-owned consumer account, with the unique index that permits one consumer account per AUTH account and the CHECK constraints that refuse an unknown status, an unexplained restriction, a deletion state with no recorded request, and a malformed region or locale. It creates no AUTH table and adds no column to one. Cross-domain references carry no foreign key, for the reason recorded in [data ownership](../architecture/05-data-ownership.md).

`0004_users_profile` adds the consumer profile, its languages, its media, and its preferences. Its constraints refuse a display name that would render as another one, a language outside the accepted shape, an image marked usable that the platform never measured, a rejection with no reason or a reason with no rejection, a slot outside the published maximum, and an object above the published size limit. The partial unique index over account and position excludes removed objects, so a freed slot is reusable and the removed record survives. Discoverability is `not null default false`, which is where the approved "not discoverable by default" rule actually lives.

`0005_users_availability` adds the one availability row per account. Its constraints refuse availability with no end and an end with no availability, an unknown state, and a revision below one. The index is ordered by the window end, because that is what discovery filters on.

`0006_discovery` adds the first non-`users_` product tables: `discovery_presentations`, one bounded row per viewer and candidate rather than one per impression, and `discovery_passes`, the private expiring suppression of a pair. Constraints refuse a pair with itself, a suppression that expires before it was made, a presentation that was never shown, and a last-shown instant before the first. Neither table carries a foreign key to a consumer account, because cross-domain references are stable identifiers rather than shared schema.

`0007_discovery_introductions` adds the pair state machine. Its constraints refuse an unordered pair, an initiator who is not one of the two people, a mutual row with no moment, a closure with no time or no reason, and a version below one. The unique index covers only live rows, so one pair may hold at most one open introduction and any number of closed ones.

`0008_discovery_scale_hardening` is the Phase 6.5 pair. `users_availability.available_since` records when an availability session began, distinct from `updated_at`, so discovery can rank on a value that does not move when somebody re-saves the same state; a constraint keeps it present exactly while a session is. `discovery_introductions.expires_at` bounds a pending signal, with a constraint refusing a pending row without one, a closed-reason constraint closing that vocabulary, and a mirrored partial unique index over the pair so a batch lookup is an index lookup from either side. Both columns are backfilled in the same migration before their constraints are added, so an existing development database migrates without a manual step.

`0009_messaging` adds the three MESSAGING-owned tables. `messaging_conversations` carries the ordered pair, the mutual introduction that authorized it, and the allocator that decides message order; its unique index over the pair is what makes opening a conversation idempotent without a client key. `messaging_participants` holds membership and one monotonic read position each, with a constraint refusing a read position recorded without a moment. `messaging_messages` carries two unique indexes that are both correctness rules rather than optimisations: one over conversation and sequence, which is the server's total order, and one over conversation, sender, and client message identifier, which is what makes a send idempotent. Constraints refuse a blank or oversized body, a position below one, an unordered pair, an unknown conversation state, and a client identifier outside the published bounds. Nothing carries an expiry: message retention duration is `DECISION REQUIRED / LEGAL REVIEW REQUIRED` and no correctness rule depends on physical deletion, so an approved duration can later be applied as a deletion pass without changing behaviour.

`0010_introduction_closure_evidence` relaxes one Phase 6 constraint that would have destroyed evidence. `discovery_introductions_mutual_shape_check` previously required `mutual_at` to be present exactly while the row was `mutual`, which meant an enforcement closure of a mutual introduction had to erase when the two people connected in order to satisfy it. It now requires that a mutual row has the moment and a pending row has none, leaving a closed row free to keep whichever it had. No row is rewritten and no evidence is created; a closure that Phase 8 has to perform simply stops being impossible.

`0011_safety` adds the three TRUST & SAFETY tables. `safety_blocks` records one person's block of another, with a partial unique index over the live pair so revoking sets an instant rather than deleting a row and the same pair can be blocked again afterwards. `safety_reports` carries the reporter, the subject, a provisional reason code, the reporting policy version in force, and an optimistic-concurrency version for the review transition; a unique index over reporter and client identifier makes submission retry-safe without collapsing two genuine reports, and constraints refuse a self-report, an unknown reason or state, a resolution with no moment, an unresolved report that has one, and message evidence with no conversation behind it. `safety_enforcements` is append-only: nothing updates a row, a lifted enforcement is a second record, and a constraint refuses an account restriction that names a conversation or a conversation closure that does not.

`0015_creators` adds the two CREATORS-owned tables, the first outside consumer core. `creators_accounts` holds one creator capability per AUTH principal, and the unique index over `auth_account_id` is the correctness rule rather than an optimisation: it is what makes concurrent first calls converge on one row without a lock, so the service is idempotent by construction. Its constraints refuse a status outside the ladder [ADR-0020](../decisions/ADR-0020-creator-capability-activation.md) locks, an unknown reason, an active capability with an unexplained reason or with no activation instant, and a closed capability with no closure instant. `creators_policy_acknowledgements` is append-only evidence keyed by creator, document, and version together, which is what makes re-submitting an acknowledgement a no-op that cannot rewrite when somebody agreed. Neither table carries a foreign key to `auth_accounts` or `users_accounts`, because cross-domain references are stable identifiers rather than shared schema and a cascade from another domain would erase creator state that [account deletion](../flows/account-deletion.md) says the owning domain must coordinate.

`0016_creator_profiles` adds the creator's public identity. `creators_profiles` holds one profile per capability, and the unique index over the canonical handle is the correctness rule rather than an optimisation: it is what gives a contested name exactly one owner when fifty callers claim it at once. Its constraints refuse a handle outside the canonical shape, a reserved handle that would shadow an application route, a display name or bio outside the published bounds, an unknown publication state, a published profile with no publication instant or a draft that still claims one, and a version below one. `creators_profile_links` bounds the count by its primary key over creator and position and refuses anything that is not an `https` URL without credentials, so a row that never passed through the contract still cannot carry a `javascript:` payload to a public page.

`0017_creator_catalog` adds `clubs_content`, the first PRIVATE CLUBS table. Its constraints refuse an unknown lifecycle or visibility, a title, summary, or body outside the published bounds, a published row with no publication instant or a draft that claims one, an archived row with no withdrawal instant, and a version below one. Two indexes rather than one: a partial index over creator, publication instant, and identifier restricted to published rows, which is exactly the public catalog's order so the planner needs no sort and a creator with a long history of drafts still answers from an index the size of what is public; and a full index over creator, creation instant, and identifier for the Studio list, which is every lifecycle. The creator reference carries no foreign key, for the reason recorded in [data ownership](../architecture/05-data-ownership.md).

`0018_private_clubs` adds the three remaining PRIVATE CLUBS tables and the club reference on `clubs_content`. `clubs_clubs` is unique on creator and slug together rather than on slug alone, and its constraints refuse a slug outside the canonical shape, a name or description outside the published bounds, a published club with no publication instant, and a closed one with no closure instant. `clubs_memberships` carries a partial unique index over club and member restricted to live rows, which is what permits exactly one live entitlement per person per club while leaving a revoked one in place as evidence and allowing later re-admission; its constraints refuse an unknown state or source and a revoked row with no revocation instant. `clubs_invites` stores only a digest, enforced to be a SHA-256 hex digest and unique, with constraints refusing an expiry that precedes creation, a redemption instant with no redeemer, and a row that is both redeemed and revoked. None of the three carries a foreign key to another domain.

`0019_admin_creator_enforcement` widens the enforcement vocabulary to creator decisions and adds the object a creator-scoped enforcement acted on. The scope check gains four values and the two new columns are constrained together: an object-scoped enforcement names an object and nothing else may, the identifier and type are set or absent together, and the type comes from a closed list. No existing row changes, and no enforcement already recorded means anything different than it did.

`0020_creator_admin_ordering` adds `creators_accounts_created_idx` over `(created_at, id)`. The operator list orders by exactly that and has no filter to narrow it — every creator is a candidate — so without the index PostgreSQL scanned the table and ran a top-N heapsort. That was found by reading a query plan on seeded volume rather than by reading the code, and the plan assertion is kept so a later change that loses the index fails the build.

`0021_billing_journal` adds the first BILLING tables and the first migration in the repository that creates triggers. `billing_journal_accounts`, `billing_journal_transactions`, and `billing_journal_entries` are one instance of the shared journal shape in `src/money/journal-table.ts`; PAYOUTS will instantiate the same shape under its own prefix and the two books will never share a row, as [ADR-0011](../decisions/ADR-0011-payments-payouts.md) requires. Three invariants are enforced by PostgreSQL rather than by the service that writes, because an accounting rule upheld only in application code is one bug away from being false. Currency agreement is structural: an entry carries its own currency and reaches its transaction and its account through composite foreign keys into `(id, currency)` on both, so an entry denominated differently from the transaction it belongs to cannot be inserted at all. Balance is a constraint trigger deferred to commit — entries arrive after the transaction row, so a per-statement check would reject the first one — and a second deferred trigger refuses a transaction that commits with fewer than two entries, which is the case a balance check alone would pass vacuously. Immutability is a `BEFORE UPDATE OR DELETE` trigger on all three tables, plus a `BEFORE INSERT` trigger on entries that compares the parent transaction's `xmin` against `pg_current_xact_id()`. That last one closes the mutation an append-only rule would otherwise miss completely: two entries that balance on their own can be appended to a transaction settled months earlier, changing what it says without updating any row. A correction is a new balanced transaction naming the one it corrects — through a composite key over identifier and currency, so a repair cannot be denominated differently from what it repairs — and there is no path that edits a posted row. `TRUNCATE` fires no row trigger, so the append-only property additionally assumes the application role does not hold that privilege; that is a deployment control rather than a schema one. Ordinary constraints refuse a non-positive entry amount, a currency outside the ISO 4217 shape, an unknown category, subject type, or reason, a platform account that names a subject or a subject account that names none, a correction with no target or an ordinary posting that claims one, and a transaction that corrects itself. Two partial unique indexes rather than one give account identity its meaning over a nullable subject, because PostgreSQL treats NULLs as distinct and a single index would admit two platform accounts for the same category and currency. The unique index over business type and reference is the idempotency guarantee: fifty simultaneous postings of one event produce one transaction because the database admits one, not because the losers looked first. The three trigger functions are created with `CREATE OR REPLACE` and dispatch on the firing table, so the PAYOUTS migration reuses them rather than defining a second copy that can drift.

`0022_billing_offers` adds what a creator sells and what it costs, kept apart. `billing_offers` points at a resource another domain owns by opaque identifier with no foreign key; its partial unique index over resource, type, and mode excludes retired rows, which is what permits exactly one live offer per club while letting a creator withdraw one and open another. `billing_prices` carries the amount as `bigint` minor units beside its currency and reaches its offer through a composite key over identifier and commercial mode, so a subscription price with no cadence, a one-time price that claims one, or a price whose mode disagrees with its offer are all structurally impossible rather than service checks. A second partial unique index permits one live price per offer per currency, because two would make "the price" a question with two answers at the moment somebody pays. Constraints refuse a non-positive amount, a currency outside the ISO 4217 shape, an unknown state, mode, interval, or resource type, a draft that claims an activation instant, a retired row with no retirement instant, and a version below one. Two triggers carry the immutability rule commerce needs: a published price is frozen except for its lifecycle columns, and neither a price nor an offer may be deleted. Both exist because a purchase references the exact price row it was made against, so editing one would rewrite what somebody agreed to pay and deleting one would orphan the record of it.

`0023_billing_payments` adds the payment operation, which exists before any provider is contacted. Three unique indexes carry three different guarantees: consumer, offer, and client key together make a double-clicked purchase one operation; the platform's provider idempotency key is unique outright, so one instruction can never be sent twice under two identities; and provider plus provider reference is unique among rows that have one, so two operations can never claim the same provider object. The price is reached through a composite key over identifier and currency, so the amount snapshot on the row cannot disagree with the price it was made against. A CHECK refuses `succeeded` on any row with no provider reference, which is what makes a fabricated settlement unwritable rather than merely unwritten. A partial index over the unsettled states serves the reconciliation sweep, so it stays the size of the backlog rather than the history. Two triggers again: a payment is frozen except for its lifecycle columns, and a provider reference may be set once and never repointed at a different charge; nothing may be deleted.

`0024_billing_events_subscriptions` adds the verified provider-event inbox, the subscription, and BILLING's transactional outbox. `billing_provider_events` is unique on provider and provider event identifier, which is what makes redelivery safe: the fifth copy of an event is one row and four acknowledgements. It stores a digest of the exact verified bytes rather than the bytes, so a payload can be proved later without retaining provider data indefinitely under a retention policy nobody has approved. Its claim index is partial over the two claimable states, and a lease with an owner in the settle predicate stops a worker whose lease expired mid-flight from writing over a claim somebody else now holds. `billing_subscriptions` carries two partial unique indexes that are correctness rules rather than optimisations — one live subscription per consumer per offer, and one per originating payment — so neither a redelivered activation nor a renewal racing a repair creates a second relationship. Constraints refuse a period whose end precedes its start, a period set on one side only, an ended subscription with no ending instant, and an entitling state with no paid period at all. `billing_outbox` is another instance of the shared outbox shape, drained by the same relay. Triggers again: a verified receipt is evidence and only its processing state may move, a subscription's money is frozen like a payment's, and neither may be deleted.

`0025_billing_reversals` adds refunds and disputes, and the one financial invariant no service can uphold alone. `billing_refunds` and `billing_disputes` both reach their capture through a composite key over identifier and currency — which is why this migration also adds `billing_payments_currency_uk`, hand-ordered ahead of the two foreign keys that reference it — so a reversal denominated differently from the charge it reverses cannot be inserted at all. The over-refund bound is a `BEFORE INSERT OR UPDATE` trigger that takes `FOR UPDATE` on the capture and then sums every reversal against it that is not `failed`. The lock never modifies that row; it is taken purely for the ordering it imposes, because the quantity being checked is the sum of rows other transactions are inserting at the same moment, and under `read committed` each statement inside the function takes a fresh snapshot and therefore sees whatever the previous holder committed. Fifty simultaneous full reversals of one charge queue at that lock and return the money once. The same function refuses a reversal of a capture that never settled. Both tables reach their tables through `tg_table_schema` in dynamic SQL rather than by bare name, because the function pins its `search_path` and a bare name would be resolvable by whoever set the path. `billing_refunds` is unique on payment and operator key, unique outright on the platform's provider idempotency key, and unique on provider plus provider reference among rows that have one; a CHECK refuses `succeeded` with no provider reference, which is what makes a fabricated reversal unwritable. Triggers freeze what a reversal means — its amount, currency, capture, operator, reason, and both keys — while leaving its lifecycle free, refuse repointing a provider reference once given, and refuse deletion. `billing_disputes` is unique on provider and provider dispute reference, which makes a redelivered notice one row and an out-of-order one lossless; its trigger freezes the provider's account of what happened, permits the evidence deadline to move because a provider may extend one, refuses to reopen a resolved claim, and refuses deletion. The verified-receipt freeze from `0024` is replaced with one covering the normalized amount, currency, dispute reason, and provider references this migration adds, because those are the values an inbound claim is checked against.

`0026_payouts_architecture` adds the second owner-specific journal and the disbursement records. The journal tables come from the same factory BILLING's do, and the migration re-runs the four `CREATE OR REPLACE` trigger functions from `0021` against them, so PAYOUTS inherits balance enforcement, the at-least-two-entries rule, immutability, and the same-transaction rule rather than defining a second copy that can drift. It adds one invariant BILLING has no use for: a deferred constraint trigger that refuses any transaction leaving a `creator` subject position overdrawn. A creator position is a liability, credited when revenue accrues and debited when money is reserved, held, or sent, so debits minus credits is at most zero for every one of them; a positive balance is exactly the shape a double-spend takes, and it is refused by the database rather than by the service that reserves. `payouts_recipients` is one row per creator and holds a provider reference plus a normalized capability answer — there is no column for a bank account number, a routing code, an IBAN, a government identifier, or an identity document, and an integration test asserts the column list rather than a validator, because the guarantee is the absence of the field. `payouts_instructions` carries the same three unique indexes a payment does, a CHECK refusing `paid` on any row with no provider reference, a partial index over the in-flight states for the reconciliation sweep, and triggers freezing everything that means money while leaving the lifecycle free. `payouts_outbox` is another instance of the shared outbox shape, drained by the same relay.

`0027_commerce_eligibility_tax` adds the tax snapshot to `billing_payments` and nothing else. `tax_minor` and `tax_authority` are set together or not at all — an amount with no authority is a number nobody stands behind, and an authority with no amount is a claim with no content — and a CHECK bounds the amount between zero and the gross, which is an arithmetic bound rather than a tax opinion. The payment freeze from `0023` is replaced with one covering both columns, because a tax assessment is evidence: recomputing a historical sale against today's rates would silently rewrite what somebody was charged, and a rate change is precisely the event that makes somebody want to. No journal position is written for tax, and the reason is recorded in [BILLING](../domains/billing.md) rather than left as an omission.

Migration files use the sequential index prefix, matching the committed `0000_bootstrap` and the `idx` ordering in `drizzle/meta/_journal.json`; `drizzle.config.ts` sets `migrations.prefix` to `index` so generation stays consistent. Do not mix index-prefixed and timestamp-prefixed migrations: ordering is taken from the journal, and a mixed scheme makes review order and file order disagree. Migrations run only through the explicit `pnpm db:migrate` command, never at application startup.

## Rules

- Domain owner writes its schema/migrations; another module never queries/modifies it directly.
- Every table/record has owner, data class, lifecycle/retention, indexes/constraints, audit needs, and migration rollback/forward plan.
- Prefer expand, backfill, dual-read/write if necessary, migrate consumers, verify, then contract later. Never deploy destructive schema change coupled to old readers.
- Execute migrations only through the explicit Bun migration command using the committed journal/SQL path. API and worker startup never invoke migrations or schema push.
- Enforce database constraints for critical uniqueness/references alongside service validation: identity linkage, idempotency, provider event, pair state, entitlement/payment/payout references as appropriate.

## Migration flow and failure

Review ownership/privacy/performance, apply compatible schema, deploy code, run durable resumable backfill with rate limits/checkpoints, validate counts/invariants, remove old path only after compatible clients/jobs drain. Backfills are idempotent and observable. Failure pauses safely, alerts, and resumes/compensates; never use production ad-hoc direct edits without an audited emergency procedure.

## Security/concurrency/phase

Migrations use a dedicated least-privilege role, no production secrets in repo/logs, and restrict sensitive data access. Locks/timeouts and online operations protect availability. Generate and review committed SQL; never use schema push or application-startup auto-migration in any environment. Real PostgreSQL tests must run the actual migration command against an empty database, rerun it, prove constraints, and assert the exact set of tables the migrations create, so a migration that crosses a domain boundary or ships an unrelated feature fails. Each domain suite additionally asserts that the tables under its own prefix are exactly the ones it owns and that it created none outside that prefix. Domain integration tests provision their own database so the migration suite keeps starting from a genuinely empty one. Database, migration tool, and initial topology are locked; partitioning is deferred until scale and backup/RPO/RTO values remain decisions before production. See [data ownership](../architecture/05-data-ownership.md), [scale](../architecture/07-scale-and-resilience.md), [account deletion](../flows/account-deletion.md).
